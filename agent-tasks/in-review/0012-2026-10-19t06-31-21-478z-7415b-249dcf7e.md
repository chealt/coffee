## Root cause

False positive from the error scanner, same class as tasks 0007/0010 — not a production failure.
The line is a benign `INFO` log from the Kolo Coffee parser (roaster 296,
`packages/webshop-item-processor/src/parsers.js`, `Missing origin region: ${regionText}`). For the
product `https://kolocoffee.eu/products/panama-bambito-estate` the parser correctly identifies the
origin country as Panama (`originCountryId: 16`), but no Panama region in
`data/originRegions.json` matches: the product text only names the farm ("Bambito Estate"), and
Panama's known regions are `bajo mono`, `boquet`, `boquete`, `volcan`, `volcan baru national park`.
Logging and storing `originRegionId: null` for such data gaps is by design — the item is still
recorded (visible in `priciestCoffees.json` with `origin_region_id: null`).

The scan only flagged it because the product description contains "exceptional" (twice), which the
old `ERROR_PATTERN` (`(?i)(error|exception|unhandled|timed out|fail)`) matched as the substring
`exception`. Verified against the sample line: the old pattern matches, the fixed pattern
(`(?i)(errors?\b|exceptions?\b|fail(ed|ing|ures?|s)?\b|unhandled|timed out)`) does not.

## Fix

No code change needed: the word-boundary fix for `ERROR_PATTERN` is already merged on main
(commits 0c06f5a2 "fix(0007)" and 57c0af1c "fix(0010)"), which prevents this signature — and the
other "exceptional" INFO signatures — from being re-created by future scans. Nothing to change in
the parser: it works as intended.

Optional follow-up for a maintainer (out of scope here): add a Panama region for the Bambito
farm area (Renacimiento district, Chiriquí) to the production database if region-level data for
this coffee is wanted.
