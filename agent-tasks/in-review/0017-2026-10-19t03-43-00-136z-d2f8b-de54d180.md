## Root cause and fix

**Not a production error — false positive from the error scanner.** The sample messages are
healthy `INFO` logs from the `webshopItemProcessor` handler (`packages/webshop-item-processor/src/index.js`):
they show items for Manhattan Coffee Roasters (roaster 305) that parsed successfully and were handed
to `recordWebshopItemDetails` for storing. Manhattan product URLs use the
`/product/coffees/exceptional/...` path segment, and the substring `exception` inside `exceptional`
matched the scanner's `ERROR_PATTERN` at the time (`(?i)(error|exception|unhandled|timed out|fail)`,
used in the CloudWatch Logs Insights `filter @message like /…/` query), so these benign INFO lines
were clustered as errors (8 occurrences; same root cause behind tasks 0001, 0004, 0006, 0007, 0010
and 0018–0019).

**Fix (already merged via tasks 0001/0007/0010, commits 4ffdde7d and 0c06f5a2):** the
`ERROR_PATTERN` in `packages/error-scanner/src/lib/aws.js` now anchors every alternative with word
boundaries — `(?i)(errors?\b|exceptions?\b|fail(ed|ing|ures?|s)?\b|unhandled|timed out)` — so
`exceptional` no longer matches, while real error-level entries (including the `\tERROR\t` level tag)
still do. The scans since 2026-10-23 confirm this signature has not reappeared.

**Reproduced** by evaluating the old and new pattern against the sample log messages plus real error
messages from other tasks: old pattern flagged 2/2 healthy Manhattan INFO logs; the current pattern
flags 0/2 of those and still matches 6/6 real errors. `yarn lint` and `yarn format:check` pass.
No code change was needed on this task — it duplicates the already-merged pattern fix.
