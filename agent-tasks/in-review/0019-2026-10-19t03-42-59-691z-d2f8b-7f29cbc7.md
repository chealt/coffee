## Root cause and fix

**Not a product error — a false positive from the error scanner, already fixed on main.** The
signature is the benign `INFO` log `Parsing item page: <url>` that every item parser emits
(`packages/webshop-item-processor/src/parsers.js`). It only matched the scan's error filter
because the Manhattan (roaster 305) product URLs live under
`manhattancoffeeroasters.com/product/coffees/exceptional/…` and the old `ERROR_PATTERN`
(`(?i)(error|exception|unhandled|timed out|fail)` in `packages/error-scanner/src/lib/aws.js`)
matched `exception` as a bare substring inside "exceptional". The invocations in the samples
(`d2f8ba2a…`, `8eb7532a…`) completed successfully end-to-end — task 0010's sample from the same
invocations shows `recordWebshopItemDetails` recording bombe/el-paseo with full details.

**Reproduction:** ran the current `ERROR_PATTERN` (`(?i)(errors?\b|exceptions?\b|fail(ed|ing|ures?|s)?\b|unhandled|timed out)`)
against both sample lines — no match (the old pattern matched both). Real error messages
(`\tERROR\tInvoke Error`, `TypeError: fetch failed`, `Task timed out …`, `Uncaught Exception`,
`UnhandledPromiseRejection`) still match.

**Fix:** none needed beyond the already-landed word-boundary fix from task 0010 / #83
(commit 57c0af1c), which prevents new tasks with this signature from being created. Tasks 0017
and 0018 are the same false positive from the same invocations and can be closed alongside this
one.
