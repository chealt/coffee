## Root cause and fix

**Not a production error — false positive from the error scanner.** The sample messages are
healthy `INFO` logs from the `recordWebshopItem` → `webshopItemProcessor` → `recordWebshopItemDetails`
pipeline for Manhattan Coffee Roasters (roaster 305), whose product URLs use the
`/product/coffees/exceptional/...` path segment. The scanner's `ERROR_PATTERN`
(`(?i)(error|exception|unhandled|timed out|fail)`, used in the CloudWatch Logs Insights
`filter @message like /…/` query) matched the substring `exception` inside `exceptional`, so every
INFO log mentioning one of those URLs was clustered as an error (same root cause behind tasks
0001, 0004, 0007, 0010, 0017–0019 and 0021).

**Fix:** in `packages/error-scanner/src/lib/aws.js`, anchor the `exception` alternative with word
boundaries — `\bexceptions?\b` — so `exceptional`/`exceptionally` no longer match, while real
messages ("Unhandled exception", "Exception:", "exceptions occurred", …) still do. `error`,
`unhandled`, `timed out` and `fail` keep their substring matching (needed for `errorType`, `failed`, …).

**Reproduced** by evaluating the old and new pattern against the sample log messages plus real
error messages from other tasks: old pattern flagged 5/5 healthy Manhattan INFO logs; new pattern
flags 0/5 of those and still matches 6/6 real errors. `yarn lint` and
`yarn workspace @centralbeans/error-scanner format:check` pass.
