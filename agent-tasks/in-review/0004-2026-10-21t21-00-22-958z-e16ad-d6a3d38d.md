## Root cause and fix note

Not a production defect in the lambdas — a false positive in the error scanner.

`invokeFlagRemoved` works as designed: it logs an INFO line for every non-removed coffee
with a webshop item link and fans out to `flagRemoved`, which correctly leaves in-stock
coffees alone (verified: the sample Manhattan pages return 200 and contain "In stock").
However, Manhattan Coffee Roasters product URLs contain the category segment
`/product/coffees/exceptional/...`, and the substring "exception" inside "exceptional"
matches the error scanner's `ERROR_PATTERN` (`(?i)(error|exception|unhandled|timed out|fail)`),
so these benign INFO lines were classified as errors (68 occurrences; the same false
positive also hits `/aws/lambda/flagRemoved` "Checking coffee: <url>" lines).

Fix: in `packages/error-scanner/src/lib/aws.js`, the pattern now requires "exception" to
not be followed by "al": `(?i)(error|exception([^a]|$)|unhandled|timed out|fail)` —
lookaheads are unavailable because Logs Insights uses the Hyperscan engine. Verified the
pattern still matches real error messages (Error/fail/timed out/unhandled/exception with
trailing non-"a" char) while excluding the Manhattan "exceptional" URLs.
