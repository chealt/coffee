## Root cause

**False positive from the error scanner, not a production failure — duplicate of tasks 0006/0007/0010,
already fixed on `main`.** Both sample lines are benign `INFO` logs from `webshopItemProcessor`'s
handler (`logger.info(\`Processing ${url}\`)`) for Manhattan Coffee Roasters (roaster 305), whose
product URLs live under `/product/coffees/exceptional/<name>/`. The substring `exception` in
`exceptional` matched the scanner's old `ERROR_PATTERN` (`(?i)(error|exception|unhandled|timed
out|fail)`), so these lines were returned by the Logs Insights error query and clustered into this
task by the 2026-10-22 scan (before the pattern fix merged). The word-boundary fix landed in
`packages/error-scanner/src/lib/aws.js` via #77, #81 and #83 (commit 57c0af1c):
`(?i)(errors?\b|exceptions?\b|fail(ed|ing|ures?|s)?\b|unhandled|timed out)`.

**Reproduction/verification:**

- The current `ERROR_PATTERN` no longer matches either sample line (checked with Node's `RegExp`
with the `i` flag), while still matching real errors (`TypeError: fetch failed`, `Uncaught
Exception`, `\tERROR\t` level tags, `Task timed out`, `SomeException: bad`).
- `ROASTER_ID=305 yarn workspace @centralbeans/webshop-item-processor test` runs the live shop:
it emits the exact `Processing https://manhattancoffeeroasters.com/product/coffees/exceptional/bombe/`
INFO line and parses the item successfully (price 20.17 EUR / 300 g, Ethiopia, sidama region,
washed, taste notes found). `el-paseo` is no longer listed in the shop. No parser errors for any
`coffees/*` URL.

**Fix:** no new code change required — the scanner fix from 57c0af1c already prevents this
signature from being re-created by future scans; this task only needed verification and closure.

Out of scope (pre-existing, unrelated to this signature): the shop now lists one
`/product/bundles/the-roses-coffee-advent-calendar/` URL which fails parsing with "Missing
details"; that is a separate filter/parser gap in the Manhattan webshop-processor parser.
