## Root cause and fix

**Not a product error — a false positive from the error scanner.** The signature is a benign
INFO log from `recordWebshopItemDetails` recording a successfully parsed product. It was only
matched by the scan's error filter because the product URLs live under
`manhattancoffeeroasters.com/product/coffees/exceptional/…`, and `ERROR_PATTERN`
(`(?i)(error|exception|unhandled|timed out|fail)` in `packages/error-scanner/src/lib/aws.js`)
matches `exception` as a bare substring, so "exceptional" trips it.

Reproduced by running the old and new pattern over the task's sample lines: old pattern matches
both samples; new pattern does not, while still matching `TypeError: fetch failed`,
`Uncaught Exception`, `ERROR Invoke Error …`, and `Task timed out`.

**Fix:** `ERROR_PATTERN` now uses `exceptions?\b` — the trailing word boundary excludes
"exceptional" but still matches "Exception(s)". `error`, `fail`, `unhandled`, and `timed out`
stay unanchored because real messages contain `TypeError`, `failed`, etc. This also stops the
same false positive for the other Manhattan "exceptional" URL signatures (e.g. tasks 0001,
0004, 0006) from being re-created by future scans. Verified via `node --input-type=module`
against the exported `ERROR_PATTERN` and with `yarn lint`.
