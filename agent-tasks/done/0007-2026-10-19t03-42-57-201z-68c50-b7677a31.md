## Root cause

False positive from the error-scanner, not a production failure. The Manhattan (roaster 305) webshop
categorizes coffees under `/product/coffees/exceptional/<name>/`, and the substring "exception" in
"exceptional" matched `ERROR_PATTERN` (`(?i)(error|exception|unhandled|timed out|fail)`), so these
plain `INFO` lines from `recordWebshopItem` were returned by the Logs Insights error query and
clustered into this task. Evidence that the lambda itself is healthy: the same invocation
(68c509b7) logged the follow-up INFO line "Recording webshop item page ..." 2.4s later (task 0006,
same false positive), both sample URLs return HTTP 200, and `ROASTER_ID=305 yarn workspace
@centralbeans/webshop-item-processor test` parses all 11 current Manhattan items successfully.

## Fix

`packages/error-scanner/src/lib/aws.js`: require a trailing word boundary on the ambiguous keyword
branches — `(?i)(errors?\b|exceptions?\b|fail(ed|ing|ures?|s)?\b|unhandled|timed out)` — so
"exceptional" no longer matches "exception", while real errors keep matching (the Lambda text-log
level tag `\tERROR\t`, `TypeError`/`ReferenceError` stack lines, "failed", "failures", "timed out",
"UnhandledPromiseRejection"). Verified against the two sample INFO lines (no match) and a battery of
real error messages (all match). Task 0006 is the same false positive from the same invocations and
can be closed alongside this one.
